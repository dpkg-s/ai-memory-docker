# 访问日志进记忆库（随 FNS 同步）

> 2026-11-08 落地。一句话：**把控制台「访问日志」的存储从容器配置卷挪进 vault，
> 变成记忆库里的一个文件，由 `fns-sync` 当附件同步到各端**。

## 为什么要这么做

控制台的访问日志（`audit.jsonl`）原本落在 `/config`（`am-conf` 卷）里，只有
跑着控制台的那台机器能看见，容器重建虽然不丢，但：

- 换台设备看不到「谁在什么时候进过库」；
- 手机/平板上的 Obsidian 也没有这份记录；
- 备份只覆盖 vault，日志要单独记着去哪儿捞。

放进 vault 之后，它就是一个普通文件 —— FNS 本来就在同步 vault，于是日志自动
跟着走，备份也自动覆盖。代价见下文，不是白拿的。

## 怎么开

### compose

```yaml
  ai-memory-web:
    environment:
      AI_MEMORY_WEB_FNS_LOG: /fns-state/sync-events.jsonl
      # 相对路径按 vault 解析（= AI_MEMORY_DIR），不必硬编码 /vault
      AI_MEMORY_WEB_AUDIT: 附件/日志/audit.jsonl
    volumes:
      - am-conf:/config
      - fns-state:/fns-state:ro
      # 🔴 日志要落进 vault，这一卷必须是**可写**的（默认那份示例是 :ro）
      - vault:/vault
```

### Quadlet / systemd（lyw-nas 的实际形态）

`/etc/containers/systemd/dpkg-ai-memory-web.container`：

```ini
Environment=AI_MEMORY_WEB_FNS_LOG=/fns-state/sync-events.jsonl
Environment=AI_MEMORY_WEB_AUDIT=附件/日志/audit.jsonl
Volume=/opt/dpkg/ai-memory/vault:/vault:z
```

改完 `systemctl daemon-reload && systemctl restart dpkg-ai-memory-web.service`。
SELinux 主机上小写 `:z` 不能省（大写 `:Z` 会给容器独占标签，把 MCP 容器锁在外面）。

### 为什么是相对路径

`AI_MEMORY_WEB_AUDIT` 支持相对路径、按 `AI_MEMORY_DIR`（vault）解析。绝对路径
照旧可用（老部署零影响）。这样写的好处是同一份配置在两种环境里都成立：

| 环境 | `AI_MEMORY_DIR` | 实际落点 |
| --- | --- | --- |
| 容器 | `/vault` | `/vault/附件/日志/audit.jsonl` |
| 本机开发（8890） | `D:\ai记忆` | `D:\ai记忆\附件\日志\audit.jsonl` |

写死 `/vault/...` 时本机开发会静默落到一个不存在的位置，改错了也不报错 ——
这是最难查的一类失效，所以刻意不用。

## 三个代价（开之前请读完）

1. **一次工具调用 = 一次上传**。每次 MCP 工具调用都会追一行审计，文件随即变化，
   FNS 防抖 500ms 后上传整个文件。审计文件本身有界（2 MB 封顶压到最近 1500 条），
   单次上传量不大，但**同步事件会被刷满** —— 「日志」页右栏一天可能出现几百条
   `upload`，那是真实现象，不是故障。想安静点就把 `AI_MEMORY_WEB_AUDIT` 留空。
2. **可读面扩大到所有能读 vault 的端**。这份文件是「谁、什么时候、从哪个 IP、
   用哪枚令牌、动了哪条笔记」—— 等于一张侦察地图。多一台设备同步到本地，就多
   一个能读到它的地方。控制台里的 `/api/audit` 仍然是 admin 专属，但**文件本身
   的文件系统权限就是同步边界**。
3. **同一个 vault 只能有一个写者**。两台机器各跑一个控制台、都往同一个
   `audit.jsonl` 追加，FNS 的冲突策略（只兜「同时改同一篇」）兜不住这种持续追加，
   结果是后写的一方把另一方的行覆盖掉。多控制台部署时请**只在一台上打开**这个开关。

## FNS 同步日志为什么不一起搬

`sync-events.jsonl` 的写者就是 `fns-sync` 自己。放进 vault 会形成闭环：

```
写一行事件 → vault 里的文件变化 → watcher 上传 → 产生一条 upload 事件
          → 又写一行 → ……（无限）
```

所以它留在 `/state`（`fns-state` 卷），控制台以**只读**方式挂到 `/fns-state`
读同一份文件 —— 两个写者会争「谁是最后一行」，这是当初就不让控制台写它的原因。

如果确实需要把同步历史也带走，正确做法是**归档快照**：定期把已经结束的事件
轮转成 vault 里的只增不改文件（如 `附件/日志/fns-sync-YYYYMMDD.jsonl`），
快照一旦写完不再变动，就不会再触发自己。这条留作后续，当前未实现。

## 验收

不依赖登录（控制台登录后也能直接看）：

```bash
# ① 容器日志里应当有一行落点说明
podman logs dpkg-ai-memory-web 2>&1 | grep 访问日志落点
#   访问日志落点 /vault/附件/日志/audit.jsonl —— 位于记忆库内，fns-sync 会把它当附件同步到各端

# ② 宿主机上能看到这个文件（还没有过访问时不存在，属正常）
ls -l /opt/dpkg/ai-memory/vault/附件/日志/

# ③ 界面「日志」页顶部状态行会显示「访问日志在记忆库内（随 FNS 同步）」
#    不显示 ⇒ 落点不在 vault；显示「不可写」⇒ 卷挂成了只读或 SELinux 标签不对
```

## 回滚

删掉 `AI_MEMORY_WEB_AUDIT` 这一行（落点自动回到 `/config/audit.jsonl`）、
把 vault 挂载改回 `:ro`，重启即可。已经写进 vault 的那份文件不删也无害 ——
控制台不再写它，fns-sync 也不会因为别的端删除它而搞出意外。
